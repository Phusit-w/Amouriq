# Elementor's built-in Element Cache can serve stale content after a direct `_elementor_data` write — only a real theme switch (or plugin activate/deactivate) clears it

This page's whole build workflow writes `_elementor_data` directly via `update_post_meta()` (see ADR-0001/0003 — there's no Elementor UI editing involved, content is generated by one-off PHP scripts). This bypasses Elementor's own save pipeline entirely, which turned out to matter for one specific feature: Elementor ships a built-in **Element Cache** module (`wp-content/plugins/elementor/modules/element-cache/module.php`) that can cache an individual element's rendered HTML via a `[elementor-element k="..." data="..."]` shortcode mechanism, with a configurable TTL (`elementor_element_cache_ttl` option — 24 hours on this install).

**What happened**: during ticket 05, `_elementor_data` was rewritten correctly (verified directly via `wp-cli post meta get` and even via a standalone PHP script that manually instantiated the widget and called `print_element()` — both confirmed the fix was in the data), but the *live rendered page* kept showing old, pre-fix content for at least one element. Hours of tracing through Elementor's rendering pipeline (kses, the WYSIWYG control, dynamic-tag parsing, `elementor/frontend/the_content`, `elementor/widget/render_content` — all confirmed clean via runtime hook dumps) eventually found a `do_shortcode_tag` frame in the render backtrace, traced to this Element Cache module.

**The trap**: this cache is cleared by `Plugin::$instance->files_manager->clear_cache()`, which is hooked to `activated_plugin`, `deactivated_plugin`, `switch_theme`, and `upgrader_process_complete` — **and nothing else**. It is **not** cleared by:
- `update_post_meta()` (how this page's content is always written)
- WP Fastest Cache's own cache directory deletion (`rm -rf wp-content/cache/all/castile`)
- a cache-busting query string on the request

**Decision / the fix**: this page's build routine already does a real theme switch (`pcoursewebbs` → `hello-elementor-child` → back) for every content-verification round (see ADR-0002) — and that switch **does** clear the Element Cache, since `switch_theme` is one of its clear-cache triggers. The ticket-05 bug only surfaced because several content-fix iterations happened back-to-back without an intervening theme switch, letting a stale first-attempt render sit cached for the whole session.

**Going forward**: if a content change stops showing up on `/castile/` despite a confirmed-correct `_elementor_data` write (checked directly via wp-cli) and a cleared WP Fastest Cache directory, don't assume the write is wrong — do one real theme switch (to the other theme and back) before debugging further. This is now a standard step worth doing as part of every verification round on this page, not just when something looks stale.
