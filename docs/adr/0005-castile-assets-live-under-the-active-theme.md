# CASTILE's supplementary CSS/JS live under `pcoursewebbs` (the real active theme), not `hello-elementor-child`

Tickets 03–06 built the CASTILE page's supplementary CSS/JS (`amq-castile.css`/`.js`, `amq-castile-buying-block.css`/`.js` — the scroll animations, the buying block's own styling, the FAQ accordion's disclosure marker, the Section 15/22 responsive stacking, the sticky mobile cart bar) as files under `wp-content/themes/hello-elementor-child/assets/`, enqueued via `get_stylesheet_directory()` / `get_stylesheet_directory_uri()`. Every verification round during those tickets temporarily activated `hello-elementor-child` before checking anything (see ADR-0002), so the files were always found — the whole build-and-verify loop never once rendered the page under the theme real customers actually see.

**What this hid**: `get_stylesheet_directory()` resolves to whichever theme is *currently active* — it is not a fixed path. The real production theme, `pcoursewebbs` (display name "Premium Course Web BS"), never had copies of these files. On production, `file_exists()` on the CSS/JS paths returned false and the whole conditional enqueue silently no-opped. Customers saw: the buying block's scent/size buttons rendered as bare inline text links with no card/button styling, the product image unconstrained and oversized, the Add to Cart button as a plain text link, and the FAQ accordion showing the browser's default disclosure triangle instead of the designed `+`/`−` marker. Everything else on the page still looked correct, because Elementor generates its own per-widget CSS from field settings regardless of theme — only the *supplementary* hand-written CSS/JS was affected.

A second, compounding issue found while fixing this: `amq-castile.css` and `amq-castile-buying-block.css` both declared `['amq-woocommerce']` as a `wp_enqueue_style` dependency — a base stylesheet handle registered only in `hello-elementor-child/functions.php`. An unmet WordPress style dependency doesn't just skip the missing dependency; it silently prevents the *depending* stylesheet from printing at all. So moving the files alone wasn't sufficient — the dependency also had to be dropped, since `pcoursewebbs` (a near-empty Blocksy child theme) never registers that handle and has no equivalent base stylesheet to depend on.

**Decision**: Moved (not copied) all four files to `wp-content/themes/pcoursewebbs/assets/{css,js}/`, and removed the `amq-woocommerce` dependency from both `wp_enqueue_style()` calls. No PHP enqueue logic needed to change beyond that — `get_stylesheet_directory()` already resolves correctly to whichever theme is active; it was purely a matter of where the physical files lived.

**Consequence, worth remembering**: the CASTILE page's supplementary CSS/JS is now *only* present under `pcoursewebbs`. If this site's theme redesign (the reason `hello-elementor-child` exists at all — see ADR-0002) ever actually goes live, these four files need to move again, back to `hello-elementor-child`, at that time — this was a deliberate choice (fix today's real customers now, defer the rework to if/when the redesign switch actually happens) over keeping duplicate copies in both themes indefinitely to avoid ever having to move them again. Whoever picks up that eventual switch should search for `amq-castile` under `pcoursewebbs/assets/` as a checklist item.

**Also found, not fixed (separate, out of scope)**: the Single Product page's own custom template and styling (`amouriq-single-product.php`, `hello-elementor-child/woocommerce/single-product.php`) has the exact same theme-dependency problem — its overrides also only exist under `hello-elementor-child`, so the live production single-product page is *also* rendering with Blocksy's default template, not the customized one. This predates and is unrelated to the CASTILE work; flagging it here since it was discovered as a side effect of investigating this same class of bug, not something this ticket's scope covers.
