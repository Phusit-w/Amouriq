# Elementor's "CSS Classes" Advanced-tab setting doesn't render — target `.elementor-element-<id>` instead

Elementor's documented way to hook custom CSS/JS onto a specific widget or container without leaving Elementor's editable-field model is the Advanced tab's "CSS Classes" control. Verified against this site's actual installed Elementor plugin source (`wp-content/plugins/elementor/includes/elements/container.php` registers it as `css_classes` on Containers; `wp-content/plugins/elementor/includes/widgets/common-base.php` registers it as `_css_classes`, underscore-prefixed, on Widgets — inconsistent between element types, first surprise). Setting either key correctly in `_elementor_data` and confirming it round-trips through `update_post_meta()` still produced **no trace of the class in the rendered front-end HTML**, on both container and widget elements, checked directly against the raw cache file on disk (ruling out any page-cache staleness). This Elementor version ships an "atomic-widgets" / class-manager system (visible in its bundled `editor-editing-panel` JS bundle) that appears to have superseded the classic custom-class control at render time, at least in this install's configuration.

**Decision**: Don't use `css_classes`/`_css_classes` for hooking presentation-only CSS/JS onto specific Elementor elements on this site. Instead, target Elementor's own **always-rendered** `.elementor-element-<id>` class (and `data-id="<id>"`) — this is core Elementor rendering behavior, not a togglable feature, confirmed present on every element regardless of the above. Capture the relevant element ids at content-build time (the one-off generator script that writes a page's `_elementor_data` also collects ids by animation role) and bake them as literal selectors into the page's dedicated CSS/JS files.

**Consequence**: these selectors are specific to the exact elements built for this content, not a reusable utility class — if an element is deleted and recreated in the Elementor editor (not just edited in place, which preserves the id), its animation silently stops working rather than erroring, and the CSS/JS/id-manifest need regenerating together. Applies to all remaining CASTILE page tickets (04, 05, 06) that add scroll animations or JS-driven behavior to specific Elementor elements.
