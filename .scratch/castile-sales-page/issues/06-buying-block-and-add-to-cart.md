# 06: Buying block, sticky cart bar, and Add to Cart (Section 19)

**What to build:** The interactive scent × size buying block, wired to the real WooCommerce cart, plus the mobile sticky Add to Cart bar — the only stateful, code-driven part of the page.

**Blocked by:** 01 (Scent/size resolver function + PHPUnit harness), 02 (CASTILE page + navigation wiring)

**Status:** done — see comments

- [x] Section 19 is built as a custom Elementor widget with a scent selector (Lavender / Rosemary / Rose Geranium), a size selector (100 / 250 / 500 ML), and a quantity stepper
- [x] Selecting a scent swaps the packshot image, product name, and essential-oil label to match the corresponding real product, using `amq_castile_resolve_selection()` from ticket 01 — all 9 scent×size combinations are precomputed server-side via that function at render time and embedded as JSON; the client only does a lookup, no per-click request (see comments)
- [x] Selecting a size swaps price and SKU to match the corresponding real variation, with no page reload
- [x] The page loads with Lavender pre-selected and a sensible default size pre-selected (100 ML, the smallest — same "first sorted variation" default convention the Single Product page already uses)
- [x] Clicking Add to Cart adds the exact selected product + variation + quantity to the real WooCommerce cart via the standard AJAX add-to-cart action, reusing WooCommerce's cart-fragments refresh so the header cart icon count updates without a page reload — reuses the site's existing `amq_add_to_cart` action (see comments) rather than a new endpoint
- [x] The customer remains on `/castile/` after adding to cart, with a visible success indicator (matching Add to Cart behavior elsewhere on the site)
- [x] A mobile sticky Add to Cart bar appears under ~860px viewport width once `#hero` has scrolled out of view, driven by an IntersectionObserver plus a media query listener (not cached scroll offsets), and hides again when scrolled back above the hero — targets Ticket 03's Hero section by its baked-in `.elementor-element-e03a679` class rather than a literal `#hero` id (see comments)
- [x] The sticky bar reflects the currently selected scent, size, and price
- [x] Selecting an out-of-stock combination (per `amq_castile_resolve_selection()`) is handled — not silently allowed to add to cart. Verified by code inspection, not live reproduction: all 9 real combinations in the current catalog are in stock, so there's no real out-of-stock data to click through (see comments)

## Comments

- **Widget registration gotcha**: the widget class initially lived directly in `wp-content/mu-plugins/`, which WordPress auto-loads at boot — before Elementor's `\Elementor\Widget_Base` class exists, so it fataled the whole site immediately (`Class "Elementor\Widget_Base" not found`, thrown from inside `wp-settings.php`'s mu-plugin loader). Fixed by moving the class file into `wp-content/mu-plugins/amq-castile/` (a subdirectory — WordPress's mu-plugins auto-loader only includes top-level `.php` files, never subdirectories) and `require_once`-ing it from inside the `elementor/widgets/register` callback, which only fires once Elementor has actually booted. Caught before it ever reached a committed state — confirmed by re-fetching `_elementor_data` via wp-cli, which fataled identically until this was fixed.
- **Reused, not duplicated, the site's Add to Cart AJAX endpoint**: `amouriq-bestsellers-carousel.php` already registers `wp_ajax_amq_add_to_cart` / `wp_ajax_nopriv_amq_add_to_cart` (`amq_handle_add_to_cart()`), used by both the Single Product page (`amq-single-product.js`) and the bestsellers carousel. The buying block's JS (`amq-castile-buying-block.js`) calls this exact same action with the exact same request shape (nonce action `amq_add_to_cart`, `product_id`/`variation_id`/`quantity` fields) instead of adding a second, parallel add-to-cart implementation — same cart behavior everywhere on the site by construction, not by convention. `document.body.dispatchEvent(new CustomEvent('wc_fragment_refresh'))` is copied verbatim from `amq-single-product.js`'s already-working pattern; confirmed WooCommerce's own `cart-fragments.js` listens for exactly this event name via jQuery's `.on()`, which does receive plain `dispatchEvent`-fired events of the same name (not just jQuery-triggered ones).
- **End-to-end verified live**, not just rendered: with `hello-elementor-child` temporarily active, POSTed the real AJAX add-to-cart request (Lavender, 100 ML, qty 2) with a fresh guest cookie jar, got back `{"success":true,"data":{"cart_count":2}}`, then loaded `/cart-page/` (the site's actual cart page — not `/cart/`, which 404s here) with the same cookie jar and confirmed "Lavender" and "100 ml" actually appear in the cart. Also POSTed an invalid `product_id` and got the expected `{"success":false,...}` rejection. The guest session's cookie jar was discarded afterward (no persistent test data left in any real cart).
- **`#hero` target**: ticket 03's Hero section container was already committed with no HTML `id` (its Elementor "CSS ID" field was never set). Rather than retroactively editing already-shipped ticket 03 content to add one, the sticky bar's IntersectionObserver targets `.elementor-element-e03a679` — Hero's own baked-in Elementor element class, same targeting approach ADR-0003 already established for this page's other supplementary JS. If ticket 03's Hero section is ever deleted and recreated in the Elementor editor (not just edited in place), this specific selector would need updating — same caveat ADR-0003 already documents for every other tracked id on this page.
- **Real catalog image mismatch found, not fixed**: `amq_castile_resolve_selection()` returns each variation's real WooCommerce image, and all three Lavender variations (100/250/500 ML) resolve to filenames like `Organic-castile-soap-rosemary-*.webp` — the live catalog's Lavender product variations appear to be attached to Rosemary product photos. This is live commerce/catalog data outside this ticket's scope to silently reassign; flagging it here for the site owner rather than guessing at a fix. Everything else about the combo (name, price, SKU, stock) is correct for Lavender — only the photo is wrong.
- Superior to the design brief's own interim state here: the brief's `README.md` flags that "100 ML and 250 ML packshots currently reuse the 500 ML bottle image per scent, as an interim stand-in" — this build doesn't have that limitation, since it uses each real WooCommerce variation's own distinct image rather than the three static packshot PNGs bundled with the design handoff (which were never imported for this ticket, since they'd have been a downgrade from the real live data already available).
- New CSS/JS files: `assets/css/amq-castile-buying-block.css`, `assets/js/amq-castile-buying-block.js` (child theme), enqueued by `amouriq-castile-buying-block.php` on `is_page('castile')`, same conditional-enqueue pattern as `amouriq-castile-page-assets.php`. New mu-plugins: `amouriq-castile-buying-block.php` (registration/enqueue) and `amq-castile/class-amq-castile-buying-block-widget.php` (the widget class).
- Verified end-to-end the same way as tickets 02-04: temporarily activated `hello-elementor-child` (user granted standing permission for the rest of this session rather than asking each time), cleared `wp-content/cache/all/castile`, curled `/castile/`, confirmed no PHP fatal/warning/notice, the widget's markup/assets/embedded JSON all present and valid — then switched back to `pcoursewebbs` immediately after and cleared the cache again.
- Section 19 inserted into `_elementor_data` as a new top-level container (background Web Light `#f5efe4`, per the README table — the design brief's own per-section notes don't override it here, unlike some earlier sections) wrapping one widget of type `amq-castile-buying-block`, immediately after Section 18 (Customer Voice). Page now has 20 top-level sections (00–19).
- **Fixed after `/code-review`** (Standards + Spec, parallel sub-agents):
  - Standards pass: no hard violations, no security issues (nonce verified, all dynamic output escaped correctly). Flagged that `addToCart()` in this ticket's JS duplicates the same request/response shape already duplicated between `amq-single-product.js` and `amq-bestsellers-carousel.js` — a pre-existing three-way pattern this ticket followed rather than introduced or fixed; left alone, since extracting a shared helper across three files is a separate refactor, not this ticket's job. Also suggested `JSON_HEX_TAG`/`JSON_HEX_AMP` on the embedded JSON's `wp_json_encode()` call as defense-in-depth against a `</script>` breakout — low real risk (all embedded data is admin/catalog-controlled, not user input) but cheap to add, so added it.
  - **Spec pass, real bugs fixed**: two of the three secondary links ("ดูส่วนประกอบทั้งหมด" and "ข้อมูลการจัดส่ง") both pointed at `#faq` — a copy-paste artifact, not intentional, and neither has real matching content there. Changed both to inert `href="#"` rather than a wrong-but-real-looking target (see the new inline comment in the widget's `render()`); only "ดูผลการทดสอบ" → `#evidence` was ever correct. Also added the missing "ปุ่ม...เต็มความกว้างบนมือถือ" (Add to Cart full-width on mobile) rule the brief specifies for Section 19's button — a `max-width: 640px` rule stacking the qty stepper above a full-width button, mirrored from the same breakpoint already used for `.amq-buying-block`'s own gap adjustment.
  - **Noted, not changed**: the sticky bar's breakpoint is `860px`, one pixel off the design prototype's own `859px`. Kept at 860 deliberately — it matches the *other* two `~860px` breakpoints already on this page (Section 15's image/text stack in ticket 04, and Section 22's in ticket 05), so all three respond to the same viewport width instead of flipping one pixel apart from each other. The ticket's own AC already says "~860px" (approximate), and internal consistency across the page's three responsive breakpoints matters more here than exactly matching one prototype's arbitrary pixel value.
