## Comments

- Content appended via a one-off PHP generator (`build-castile-05.php`, scratchpad-only), same approach as tickets 03/04, PLUS a whole-page retrofit pass this ticket needed that those didn't: walking every already-committed section (00–19) to find and re-wrap existing footnote marker characters (`*`, `**`, `†`, `‡`) into `<sup><a href="#fn-*">...</a></sup>` links, since those markers were authored as plain text in tickets 03/04/06 with no expectation they'd later need to become links.
- **Real content gap found and fixed while retrofitting**: the Hero's Water Loss proof card (ticket 03) was missing its `**` footnote marker entirely — the brief's Hero note block pairs `*` with the Moisture card and `**` with the Water Loss card, but only the Moisture card's `*` was ever built. Added the missing `**` as part of this ticket's pass, then let the retrofit link it like every other marker.
- **Two real bugs in the retrofit script itself, both caught before committing (not by `/code-review` this time — found through direct testing while verifying the feature actually worked)**:
  1. `foreach ($el['elements'] ?? [] as &$c) recurse($c, ...)` silently breaks PHP's reference chain — `??`'s result is a temporary value, not an lvalue, so a foreach-by-reference over it mutates a throwaway copy that never writes back into the real array. The script reported successful mutations (its own counters incremented) while the actual written JSON was completely unchanged below the top level — the fix is to `if (!empty($el['elements'])) { foreach ($el['elements'] as &$c) ... }` instead, with no `??` in the foreach subject. Worth remembering for any future script that mutates (not just reads) this page's `_elementor_data` tree.
  2. The retrofit's "undo a pre-existing manual `<sup>marker</sup>` wrap before re-wrapping" step only handled the one case ticket 04 had used (`‡`), forgetting this ticket's own `amq_footnote()` helper builds all four Section 23 definitions the same way — producing double-nested `<sup><sup><a>...</a></sup></sup>` for the other three markers. Fixed by generalizing the undo step to all four markers.
- **A third, much larger bug, in Elementor itself, not this codebase — worth documenting prominently for whoever works on this page next**: after fixing both script bugs above and rewriting `_elementor_data` correctly (confirmed correct via direct wp-cli reads and even via `create_element_instance()` + `print_element()` in an isolated PHP script), the **live rendered page still showed the old, pre-fix, un-linked marker text** for at least one element. Hours of tracing through Elementor's rendering pipeline (kses, WYSIWYG control, dynamic-tag parsing, `elementor/frontend/the_content`, `elementor/widget/render_content` — all ruled out one by one via runtime hook dumps) eventually found the real cause: **Elementor's own built-in "Element Cache" module** (`wp-content/plugins/elementor/modules/element-cache/module.php`), which caches individual elements' rendered HTML via a `[elementor-element k="..." data="..."]` shortcode mechanism with a 24-hour TTL (`elementor_element_cache_ttl` option). This cache is only cleared by `Plugin::$instance->files_manager->clear_cache()`, hooked to `activated_plugin`, `deactivated_plugin`, **`switch_theme`**, and `upgrader_process_complete` — **never** by `update_post_meta()`, WP Fastest Cache's own cache clear, or a cache-busting query string (all tested, none worked). Since this page's whole build workflow writes `_elementor_data` directly via `update_post_meta()` (bypassing Elementor's own save flow entirely — see ADR-0001/0003), this stale-element-cache trap can silently reappear on **any** future ticket for this page. **The fix, once identified, was trivial**: this page's build routine already does a real theme switch (`pcoursewebbs` → `hello-elementor-child` → back) for every verification round, and that switch **does** clear this cache — the bug only bit here because several content-fix iterations happened in a row without an intervening theme switch. **Going forward**: if content changes stop showing up on `/castile/` despite a confirmed-correct `_elementor_data` write and a cleared WP Fastest Cache, do one real theme switch (to the other theme and back) before assuming anything else is wrong.
