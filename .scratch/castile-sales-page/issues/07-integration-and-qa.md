## Comments

- **Environment outage mid-QA, not a code issue**: partway through this ticket, the local dev environment (Local by Flywheel/WP Engine) went down — nginx stayed up (502 Bad Gateway) but MySQL became unreachable even from the CLI (`wp-cli` itself failed with "Error establishing a database connection", and port 10005 refused connections directly). This is infrastructure, not anything this session's work caused — no code change, DB write, or verification step here talks to service-level infra. The site owner restarted the Local app/site's services; confirmed fully recovered (port 10005 listening again, `wp-cli` working, site returning 200) before continuing. The full purchase-path test was re-run after recovery to be safe, and passed cleanly.
- **A near-miss during the navigation check, worth recording so it isn't mistaken for a real bug later**: an early comparison of a Single Product page's header markup against `/castile/`'s showed *different* header classes (`amq-shop-header` vs `ct-header`) even though both were fetched with the same theme (`pcoursewebbs`) active — looked exactly like a real navigation-inconsistency bug at first. Turned out to be a **stale WP Fastest Cache file** for that specific product URL, left over from an earlier ticket's temporary `hello-elementor-child` verification round (`wp-content/cache/all/product/`), never cleared because this ticket's QA pass hadn't touched that cache directory before. Clearing `wp-content/cache/all/product` and re-fetching both pages fresh produced identical `ct-header` markup on both, as expected. **Lesson for future QA passes on this page**: clear cache directories for *every* URL being compared, not just `/castile/` itself — a stale cache on a *comparison* page can look identical to a real inconsistency.
- **Section 10 and Section 11 share the same background (`#fbf8f2`, Milk Oat), and Section 15/16 share another (`#4a5b32`, Olive Grove)** — flagged during the full-sequence review, then confirmed both are the *documented, deliberate* result of each ticket's own per-section color resolution (ticket 04's comments), not an accidental oversight. Two adjacent same-tone sections rely on padding/whitespace for separation rather than a color change, consistent with the design system's own stated principle that elevation/separation comes from whitespace or a hairline, not always a background swap.
- **Honest scope limitation**: this environment has no browser automation (no Playwright/Puppeteer, no way to launch a real browser and capture a screenshot or console output). Every check in this ticket that would normally want a real rendered viewport (top-to-bottom visual match against the design reference at desktop/mobile widths, JS console errors during interaction) was done as thoroughly as HTTP/DOM-text-level inspection allows instead: full HTML fetched at the relevant breakpoint-adjacent widths isn't meaningfully different from fetching once (CSS media queries render the same either way — the *markup* doesn't change with viewport, only which CSS rules apply), so the structural/copy/color verification above is as complete as this method gets, but it cannot catch a purely visual regression (e.g., an overlap or misalignment that only shows up when the CSS is actually laid out in a real browser at a real width). If real visual QA is wanted before this page goes live, it needs a human (or a browser-automation-equipped session) to actually load `/castile/` at a few widths and scroll through it.
- No code changes were needed for any of the AC items above — this ticket was pure verification, as its own description says ("No new behaviour").
